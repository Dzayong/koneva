# KONEVA — backlog eksekusi owner final

Tanggal baseline: 2026-09-27. Sumber keputusan: brief final owner 2026-09-27 di percakapan. Ini rencana kerja Codex (PM) untuk Claude (full-stack dev), bukan klaim fitur sudah selesai. Semua tes memakai data sintetis sampai owner memberi izin eksplisit untuk akun/nomor uji. Jangan sentuh stack `:13000`, production, `.env`, email, WhatsApp nyata, VPS berbayar, domain, remote, atau migrasi hidup tanpa otorisasi tersendiri.

## Keputusan terkunci

- Kanal WhatsApp: Baileys. Versi lokal `7.0.0-rc14` melewati versi perbaikan CVE-2026-48063; tetap RC dan dipantau. Tidak boleh menjanjikan bebas ban; jelaskan mitigasi dan risiko kepada pengguna.
- Commit diizinkan per topik pada branch terpisah dari `master`, default `develop`. Tidak push tanpa izin owner.
- Harga bulanan: Pelajar Rp29.000 (1 device/1.000 pesan/1 anggota); Asisten Pribadi Rp59.000 (1/5.000/1); Tim UKM Rp99.000 (3/10.000/3); Bisnis CS Rp199.000 (5/20.000, fair-use, 10 anggota). Annual ditutup untuk pembelian baru, tetapi data historis harus tetap terbaca. `umkm` lama menjadi Tim UKM. Pelanggan Pelajar lama Rp19.000 tetap dengan harga lama selama subscription aktif.
- Verifikasi Pelajar: bayar → kirim bukti → verifikasi; aturan penolakan dan masa tenggang menunggu keputusan owner. Sistem harus mengutamakan verifikasi otomatis yang dapat dibuktikan dan mengirim kasus ragu ke operator.
- Level/Misi adalah backlog setelah kesiapan lokal. Level bukan prediksi atau jaminan anti-ban. Tidak ada misi yang mengirim ke penerima tanpa persetujuan atau menghindari batas platform.
- Domain dibeli hanya setelah lokal + komunikasi API + uji VPS IP publik lolos. Uji VPS 14 hari mengukur kestabilan, bukan bebas ban. Akun uji khusus dan izin eksplisit owner wajib sebelum koneksi WhatsApp.
- Demo investor memakai data sintetis. Lengkapi halaman Syarat/Privasi yang sudah ada, consent/opt-out, retensi, kontak privasi, dan checklist PDP/PSE.

## Cara kerja dan definisi status

Claude menerima satu task harian. Setiap laporan mencantumkan: status, file terkait, cara reproduksi, tes dan hasil, lingkungan (lokal/disposable/VPS/pilot), dampak data, gap, dan blocker. `Selesai` berarti definisi selesai dan bukti di kolom task terpenuhi. Tes lokal bukan bukti LIVE. P0 yang gagal menggeser jadwal; jangan melompati gerbang atau mengurangi tes keamanan. Estimasi adalah hari-orang Claude, bukan janji kalender.

## Tahap 0 — Aman dan tertib

### Hari 1 — 2026-09-27: inventaris risiko dan siapkan commit aman (T0.1/T0.2)

**T0.1 Inventaris rahasia/backup — 0,5–1 hari.** Status awal owner: branch `master`, 108 entri worktree; setelah PM menambahkan `STATUS_PROYEK.md`, jumlah menjadi 109. Belum ada perubahan staged dan tidak terlihat remote; `k8s/secrets.yaml` tracked; arsip `wa-gateway-backup-20260925.tar.gz` tidak ada di worktree, tetapi dilaporkan ada dalam sejarah Git. Claude wajib mengonfirmasi ulang tanpa mencetak isi rahasia.

- Definisi selesai: inventaris file per nama/status; secret scan atas working tree dan sejarah dengan output redacted; `k8s/secrets.yaml` diganti dengan contoh aman/di-ignore bila berisi nilai aktif; tarball dan file sensitif lain tidak lagi reachable dari sejarah lokal setelah pembersihan yang diminta owner; tidak ada `.env*`, `sessions/`, `backups/`, data, atau secret di snapshot/commit.
- Bukti: jumlah temuan menurut kategori (nilai dirahasiakan), daftar path saja, hasil `git log --all -- <path>`/scanner redacted, verifikasi riwayat bersih, dan daftar kredensial yang harus dirotasi tanpa nilainya.
- Jika sejarah berisi kredensial aktif: jangan tampilkan atau memindahkannya ke laporan; tandai rotasi sebagai blocker sebelum push. Jangan menghubungi provider/merotasi credential produksi tanpa otorisasi. Sejarah bersih tidak membatalkan kebutuhan rotasi bila arsip pernah terakses pihak lain.
- Perubahan riwayat lokal memang diperlukan untuk membuang arsip dari semua commit. Kerjakan hanya setelah checkpoint/backup lokal aman, pastikan tidak ada remote, verifikasi seluruh perubahan worktree tetap utuh. Jangan push.

**T0.2 Branch dan commit per fitur — 0,5–1,5 hari.** Buat `develop` dari `master` sesuai default owner setelah checkpoint aman. Pecah perubahan ke commit kecil dan koheren; jangan mass-stage/commit seluruh worktree sekaligus. Mulai dari pekerjaan yang memiliki tes dan tidak bergantung pada keputusan baru.

- Definisi selesai: perubahan yang dipilih tercatat pada branch `develop`; working tree bersih untuk file yang sudah dinyatakan selesai; tidak ada secret/arsip/`.env*`/session/backup/data yang masuk commit; setiap commit punya ringkasan topik yang tepat.
- Bukti: branch + hash commit lokal, daftar path per commit, hasil scanner tanpa secret, status `git status`; tidak ada push.
- Jika satu fitur belum lulus tes, jangan masukkan ke commit “selesai”; laporkan blocker dan biarkan terpisah.

### Hari 2 — 2026-09-28: CI/checks pertama (T0.3) — 0,5–1 hari

- Jalankan seluruh suite wajib yang didefinisikan workflow CI: backend, entrypoint/Redis gated, dashboard unit/stack, typecheck dan lint. Perbaiki mismatch fixture/harness sebelum memperluas scope.
- Definisi selesai: setiap command lulus atau skip memiliki alasan dan tes pengganti yang dijalankan. Bila repo tidak punya remote (status awal tidak menunjukkan remote), status GitHub CI wajib ditulis `BELUM DAPAT DIJALANKAN`; jangan menganggap membaca YAML sama dengan CI hijau.
- Gerbang 0: hasil secret review bersih/redacted, sejarah lokal sudah dibersihkan dari arsip, branch dan commit aman, semua check lokal hijau, serta syarat rotasi sebelum push terdokumentasi.

## Tahap 2 — Level/Misi dan cost meter

### Hari 18 — Spec Level & Misi (PM) — 1 hari

- Rancangan awal misi per level: **Lv 0** amankan sesi, consent/opt-out, webhook dan kirim/terima test ke diri sendiri; **Lv 1** percakapan personal intensitas rendah ke penerima yang sudah setuju; **Lv 2** kesiapan broadcast menengah lewat verifikasi daftar consent, preview, suppression/opt-out, dan uji satu penerima; **Lv 3** kesiapan OTP/notifikasi berdasarkan uji antrean, idempotensi, rate-limit aplikasi dan observability di staging; **Lv 4** kesiapan operasional CS melalui multi-anggota/perizinan, antrean, kapasitas, eskalasi dan runbook. Media/grup hanya misi konfigurasi/uji kepada penerima/grup yang memang memberi izin; jangan otomatis membuat grup atau menambahkan anggota. Misi tidak meminta pengiriman massal untuk “memanaskan” atau meniru manusia.
- Spesifikasi level 0–4, kriteria naik berdasarkan kesiapan produk yang terukur, misi manual/otomatis per paket, progress/badge/checklist, bukti data, copy dialog bypass, audit, dan UX tanpa klaim bebas ban.
- Level mengukur kesiapan operasional produk, bukan penilaian/approval WhatsApp. User boleh memilih paksa naik level setelah dialog risiko; simpan actor/waktu/level yang dipilih/persetujuan. Bypass melewati checklist rekomendasi level saja dan tidak menaikkan hard quota server, membatalkan opt-out/consent, atau mengirim ke penerima yang tidak memberi izin.
- Definisi selesai: acceptance criteria/test cases/API/data model dan copy disetujui owner. Jika misi yang diinginkan berpotensi mengirim tanpa consent, tawarkan misi alternatif setup, test ke nomor sendiri yang diizinkan, status/monitoring, dan dokumentasi.

### Hari 19–23 — Implementasi Level/Misi — 3–5 hari setelah spec disetujui

- Backend state/misi, UI progress dan badge, audit level/bypass, tes transisi, regresi role dan tenant. Otomatisasi hanya tugas lokal yang non-messaging kecuali owner mengotorisasi skenario uji yang sah.
- Definisi selesai: semua level memiliki syarat jelas dan dapat diuji; progress tidak menyatakan aman/anti-ban; stack-local lulus.

### Hari 24–31 — Cost meter — ±7,5 hari-orang

- Implementasi/ukur metrik cgroup RAM/CPU per bot, storage per sesi dan estimasi DB per tenant, queue/volume; tanpa isi pesan/nomor pada label metrics. Jalankan benchmark sintetis idle/aktif/5 device; masukkan invoice provider dan waktu support jika tersedia.
- Definisi selesai: angka biaya per paket menunjukkan sumber, rentang, asumsi dan uncertainty; kuota fair-use tidak melebihi kapasitas/ekonomi tanpa persetujuan owner. Belum mengutip angka lokal sintetis sebagai live.
- Gerbang 2: fitur Level/Misi berfungsi lokal dan model biaya per paket tersedia.

## Tahap 3 — Uji VPS sebelum domain

### Hari 32–33 — Benchmark sizing lokal sintetis — 1–2 hari

- Jalankan 1 bot idle, 1 aktif, 5 aktif dengan fake transport dan Postgres/Redis disposable. Ukur p50/p95 RAM/CPU cgroup, storage, queue age, errors, restart/recovery. Ini mendahului pemilihan spek VPS, walaupun urutan draft awal menempatkan sewa VPS dahulu.
- Definisi selesai: rekomendasi spek + margin headroom + asumsi dan hasil skrip berulang. Owner menyetujui vendor/biaya sebelum sewa.

### Hari 34–35 — VPS disposable dan deploy — 1–2 hari setelah approval biaya

- Deploy stack terisolasi ke VPS dengan IP publik, hardening, firewall, backup/restore, monitoring, secrets dari secret manager, egress IP dicatat. Jangan gunakan domain dulu. Jangan pairing WhatsApp tanpa izin owner dan akun uji khusus.
- Definisi selesai: API internal berkomunikasi, health/readiness, backup/restore, security controls dan smoke tests lulus; bukti provider tentang IP statis/dedicated dan harga ditautkan.

### Hari 36–49 — observasi 14 hari kalender nonstop

- Setelah owner mengizinkan sesi akun uji, ukur uptime, disconnect/reconnect, auth loss, penggunaan resource/disk, perubahan IP egress dan pemulihan. Jangan gunakan “tidak kena ban” sebagai acceptance criterion. Hentikan sesi dan laporkan bila ada banned/logged-out berulang, retry storm, duplikasi, atau anomali keamanan.
- Definisi selesai: 14 hari terukur, 0 kehilangan auth tak terjelaskan/reconnect loop, semua disconnect terklasifikasi, IP provider stabil dan resource alert tersedia. Ini tetap bukti stabilitas terbatas, bukan jaminan bebas ban.
- Gerbang 3: kriteria uji terpenuhi dan owner menerima hasil → domain baru boleh dibeli. Jika sesi uji khusus belum diizinkan, gerbang belum lulus.

## Tahap 4 — Go-live infrastruktur

## Tahap 5 — Pilot terbatas

### 30 hari kalender minimum setelah Gerbang 4 dan izin owner

- Hari pilot 1: onboarding cohort kecil yang disetujui, persetujuan nomor/penerima, SOP support dan kill switch. Harian: uptime, error, reconnect, resource, send failures/duplicates, opt-out, tickets, biaya dan potensi account restriction.
- Review mingguan; hentikan onboarding jika P0 privasi/duplikasi/akses atau pembatasan akun berulang. Jangan scale untuk “menghindari deteksi”.
- Definisi selesai: satu periode billing penuh dengan data observasi, tanpa P0, support dan unit economics diketahui, umpan balik pelanggan terdokumentasi. Jika owner belum mengizinkan nomor dan pelanggan pilot, status tidak melewati Gerbang 4.
- Gerbang 5: owner menerima laporan pilot dan menyetujui lanjut/ubah/hentikan.

## Tahap 6 — Rilis umum

Karena itu, jangan menunggu pendaftaran PSE setelah rilis umum jika KONEVA masuk kriteria; minta kajian/konfirmasi hukum dan majukan pendaftaran sebelum pilot/public user bila diwajibkan.
