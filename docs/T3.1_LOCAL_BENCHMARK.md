# T3.1 — local synthetic device baseline

Date: 2026-10-19 (Asia/Jakarta)
Evidence: local Docker/WSL runs, disposable PostgreSQL 15 + Redis 7, application bot image. This is a machine-specific baseline, not production capacity guidance.

## Setup and safety boundary

- Each scenario used the real KONEVA bot process with a synthetic tenant and five synthetic device rows in a new disposable database. No production database, Redis, sessions, or `:13000` container was attached.
- Each bot had a 512 MiB memory limit. Containers had no published ports and shared a fresh Docker `--internal` network with the disposable dependencies and local probe; runtime egress was disabled.
- `KONEVA_SANDBOX=1` was set for every bot. The run also set `WHATSAPP_TRANSPORT=real` deliberately to confirm the sandbox kill-switch overrides it. Bot logs confirmed that no real WhatsApp connection was started.
- The first two validation runs measured repeated local `GET /health` requests only. The final run also enqueued 1,000 synthetic jobs per active device and ran them through the bot process's BullMQ worker. The guarded benchmark mode uses an in-memory fake socket and an allow-all pacing decision; it never opens Baileys or contacts WhatsApp.
- Queue jobs are inserted directly into disposable PostgreSQL and Redis, then processed through the real queue worker, including consent and administrative transmission checks. The public API enqueue path and anti-ban pacing are intentionally outside this synthetic throughput measurement.
- CPU and RAM percentiles use Docker cgroup stats per bot, nearest-rank p95. The final run recorded 15 idle snapshots, 6 one-device queue-load snapshots, and 5 snapshots per device during five-device queue load. All phases ran on the same host.

## Results

The repeatable script was run end-to-end twice for health-only load and once with synthetic queue traffic. RAM values are MiB per bot; CPU is Docker's per-container percentage. The spread between runs shows host noise, so these are observations rather than a stable capacity number.

| Scenario | Script run A CPU p50 / p95 | RAM p50 / p95 / max | Script run B CPU p50 / p95 | RAM p50 / p95 / max |
|---|---:|---:|---:|---:|
| 1 idle bot | 0.19% / 3.22% | 63.68 / 68.46 / 68.46 MiB | 0.21% / 4.15% | 63.74 / 68.62 / 68.62 MiB |
| 1 active bot, health probes only | 6.30% / 28.40% | 77.54 / 79.52 / 79.52 MiB | 6.54% / 12.42% | 77.22 / 78.23 / 78.23 MiB |
| 5 active bots, health probes only | 5.21% / 12.46% | 77.65 / 78.82 / 79.20 MiB | 5.44% / 12.91% | 78.03 / 79.39 / 93.11 MiB |

The final 1,000-job-per-device run produced:

| Scenario | CPU p50 / p95 | RAM p50 / p95 / max per bot | Queue result |
|---|---:|---:|---|
| 1 active bot | 71.14% / 120.73% | 146.05 / 150.10 / 150.10 MiB | 1,000 / 1,000 fake sends; 98.67 jobs/s; queue age p50 5.58 s, p95 9.73 s |
| 5 active bots | 64.28% / 102.43% | 142.30 / 154.70 / 154.90 MiB | 1,000 / 1,000 fake sends per bot; 70.10–71.39 jobs/s per bot; queue age p50 7.68–7.80 s, p95 13.55–13.78 s |

Additional observations:

- The sandbox session directory stayed empty (0 bytes). The final run's restarted bot returned HTTP 200 after 10.34 seconds. These are local observations, not a recovery SLO.
- Disposable PostgreSQL and Redis stayed reachable. The final run created 6,000 synthetic message rows; all 6,000 reached the fake transport with zero worker failures. Its `sent` status means only that the in-memory fake accepted the send call, not that WhatsApp delivered a message.
- Health-probe checkpoints reported no failed requests. During queue load, per-container CPU exceeded 100%; Docker reports CPU as core percentage, and the values reflect this host's available CPU rather than a VPS sizing guarantee.
- Bot readiness is “degraded” because the sandbox intentionally leaves WhatsApp offline; this is expected, not an application failure.

## What this does not establish

The fake transport makes queue processing measurable, but it cannot measure real WhatsApp send throughput, delivery errors/receipts, real anti-ban pacing, connected-session resource cost, session storage growth, or network/proxy behavior. It also does not measure VPS performance. Do not use these numbers alone to choose a VPS plan or promise device capacity.

The task remains **partial**: deterministic fake queue processing, queue age, send-path outcomes, empty-session storage, and a restart probe are now measured; connected-session behavior, realistic pacing, longer soak, VPS measurements, and recovery criteria remain. The repeatable disposable probe is `scripts/benchmark-device-sizing.sh`; it preserves raw samples under `/tmp` and cleans up only its own containers and network. The final validated run's raw artifacts are in `/tmp/koneva-t31-queue-final` on this machine.
